* TL;DR
:PROPERTIES:
:DESCRIPTION: A bridge that lets dovecot's passdb chain authenticate SMTP submission.
:END:

=dsmr-checkpassword-dovecot= ships a small DJB-style /checkpassword/ program,
=/var/qmail/bin/checkpassword-dovecot=, that *qmail-smtpd* exec()s on each
SMTP-AUTH attempt. Instead of validating the credential itself, the bridge asks
*dovecot* over its auth-client socket, letting dovecot's already chained passdbs
— vpopmail SQL, then =/etc/dovecot/system-passwd=, then PAM — decide.

The result: one passdb stack is the single source of truth for *both* IMAP login
and SMTP submission. In the stock DSMR stack the submission service authenticates
with =vchkpw=, which knows only vpopmail virtual accounts; a curated Unix shell
user who needs to relay outbound mail through a domain the host accepts via
=rcpthosts= + =~/.qmail-*= aliases (a domain that is *not* a vpopmail virtual
host) cannot SMTP-AUTH. This package closes that gap without moving the domain
into vpopmail and without running two divergent passdb chains.

The package installs:

- =/var/qmail/bin/checkpassword-dovecot= — the bridge (runs as the calling UID,
  i.e. the vpopmail UID qmail-smtpd runs under);
- =/usr/sbin/dsmr-smtpauth= — an admin tool to curate the system-user allow-list
  (see *dsmr-smtpauth(8)*);
- =/etc/dovecot/conf.d/99-dsmr-smtp-auth.conf= — a conffile adding a second
  auth-client listener the bridge can read.

It only changes *submission* (port 587, authenticated). Inbound port 25 is
untouched.

* Theory of operation
:PROPERTIES:
:DESCRIPTION: How the bridge sits between qmail-smtpd and dovecot, and the wire protocol.
:END:

** The flow
An AUTH attempt travels through four hops:

: MUA  --AUTH LOGIN/PLAIN over STARTTLS :587-->  qmail-submission (qmail-smtpd)
:      --fork+exec, FD3: <user>\0<pass>\0<ts>\0-->  checkpassword-dovecot
:      --AUTH PLAIN over Unix socket-->  /var/run/dovecot/auth-client-smtp
:      --chained passdbs-->  dovecot auth  -->  OK / FAIL

qmail-smtpd fork+exec()s the bridge once per attempt as a child running under the
vpopmail UID. On =OK= the bridge exec()s its argument (=/bin/true=) and exits 0,
which qmail-smtpd maps to =235=; on =FAIL= it exits 1 (=535=); on any internal
error it exits 111 (=454=). See *checkpassword-dovecot(8)* for the exit-code
contract.

** Why a second auth-client listener
Dovecot's default =auth-client= socket is mode =0600=, owner =dovecot:root= —
unreadable by the vpopmail UID the bridge inherits from qmail-smtpd. Rather than
loosen that shared socket or grant the bridge extra privilege, the package's
conffile adds a *separate* listener:

| Listener                                 | Mode | Owner             | Consumer                 |
|------------------------------------------+------+-------------------+--------------------------|
| =/var/run/dovecot/auth-client= (default) | 0600 | =dovecot:root=    | other dovecot auth users |
| =/var/run/dovecot/auth-client-smtp=      | 0660 | =vpopmail:vchkpw= | this bridge              |

The new listener matches the identity qmail-smtpd already runs as, so no new
privilege is introduced. The unique name =auth-client-smtp= avoids colliding with
any userdb-only socket configured elsewhere.

** Wire protocol — the qmail side (FD3)
After STARTTLS+AUTH, qmail-smtpd has already base64-decoded LOGIN, or split the
PLAIN =\0authzid\0authcid\0password= blob, and writes on descriptor 3:

: <authcid>\0<password>\0<timestamp>\0

This payload is trusted (qmail-smtpd has rejected malformed AUTH framing), but
the bridge still bounds-checks it: max 512 bytes, NUL-separator validation, and
control characters in the username are rejected so they cannot break the
auth-client framing downstream.

** Wire protocol — the dovecot side (auth-client)
The bridge writes its handshake first (before draining the greeting, to avoid a
deadlock if dovecot blocks on the client's =VERSION=):

: VERSION  1  2
: CPID     <bridge-pid>

After draining the server greeting up to =DONE=, it sends:

: AUTH  1  PLAIN  service=smtp  resp=<base64(\0authcid\0password)>

and maps the reply:

| Dovecot reply                 | Bridge action   | Exit | qmail-smtpd |
|-------------------------------+-----------------+------+-------------|
| =OK\t1\tuser=<canonical>=     | exec(/bin/true) |    0 | 235 accept  |
| =FAIL\t1\treason=...=         | clean reject    |    1 | 535 reject  |
| anything unexpected / timeout | transient error |  111 | 454 defer   |

The full dovecot auth-protocol spec is at
[[https://doc.dovecot.org/2.4/core/protocols/auth.html]].

* Usage examples
:PROPERTIES:
:DESCRIPTION: Managing the allow-list and verifying the bridge end-to-end.
:END:

The allow-list is curated with *dsmr-smtpauth(8)*. Use a password *separate*
from the user's Unix login.

: # dsmr-smtpauth add fade        # prompts twice, then self-verifies via the bridge
: # dsmr-smtpauth list            # authorized usernames
: # dsmr-smtpauth passwd fade     # change a password
: # dsmr-smtpauth test fade       # authenticate end-to-end, no file change
: # dsmr-smtpauth del fade        # remove

Confirm the listener exists after a dovecot reload:

: # ls -l /var/run/dovecot/auth-client-smtp
: srw-rw---- 1 vpopmail vchkpw 0 ... auth-client-smtp

Confirm submission is wired to the bridge (needs =dsmr-qmail-run >= 1.0-9=):

: # ps -ef | grep '[q]mail-smtpd' | grep checkpassword-dovecot

Test from a remote host with =swaks= — a vpopmail user (still works through the
bridge) and a system user (newly authenticatable):

: $ swaks --to ext@example.com --from fade@example.net --server host --port 587 \
:         --tls --auth LOGIN --auth-user fade@example.net --auth-password '...'
: $ swaks --to ext@example.com --from fade@deepsky.com --server host --port 587 \
:         --tls --auth LOGIN --auth-user fade@deepsky.com --auth-password '...'

Watch both logs while testing:

: # tail -f /var/log/qmail/submission/current | tai64nlocal
: # journalctl -fu dovecot

A successful auth shows =passdb(...): match= in dovecot's log and
=authuser=...= in submission's =qlogenvelope= line.

* Configuration
:PROPERTIES:
:DESCRIPTION: The conffile, the allow-list, and selecting the bridge at submission.
:END:

- =/etc/dovecot/conf.d/99-dsmr-smtp-auth.conf= :: conffile; adds the
  =auth-client-smtp= listener. Reload dovecot after changes.
- =/etc/dovecot/system-passwd= :: the system-user allow-list (passwd-file passdb).
  Owner =root:dovecot=, mode =0640=. Manage with *dsmr-smtpauth(8)*; record form
  =<user>:{SHA512-CRYPT}<hash>[:uid:gid::home:shell]=. For Unix users the
  uid/gid/home fields let the same file serve dovecot's userdb for IMAP/Maildir.
- *Selecting the bridge* :: =dsmr-qmail-run >= 1.0-9='s submission run script
  picks the bridge automatically when =/var/qmail/bin/checkpassword-dovecot= is
  executable, else falls back to =vchkpw=. This package does *not* edit the run
  script (it is owned by =dsmr-qmail-run=).

* Extension points
:PROPERTIES:
:DESCRIPTION: How dovecot's passdb chain extends the set of authenticatable users.
:END:

- *Add an authenticatable population by chaining a passdb.* The bridge inherits
  whatever dovecot's chain decides. Add a vpopmail account, an
  =/etc/dovecot/system-passwd= row (via *dsmr-smtpauth(8)*), or another
  =passdb { }= block with =result_failure = continue=, and it authenticates over
  both IMAP and SMTP-AUTH at once — never out of sync by construction.
- *Relay-only credentials.* Add a name that is not in =/etc/passwd=: the entry
  authorizes SMTP-AUTH but carries no uid/gid/home, so it has no Maildir.
- *Multi-domain senders.* =FORCEAUTHMAILFROM=1= on the submission service ties
  =MAIL FROM= to the AUTH username. A single account that must send From several
  domains is served by dropping that constraint and adding a qmail-spp
  envelope-checker with an explicit authuser→domains allowlist — out of scope for
  this package.

* Gotchas and debugging
:PROPERTIES:
:DESCRIPTION: Why an auth might fail, and how to tell which hop broke.
:END:

- *The bridge sits on disk but is never called.* Installing this package without
  =dsmr-qmail-run >= 1.0-9= leaves the submission run script on =vchkpw=. Confirm
  with the =ps= check above; bump =dsmr-qmail-run= and =qmailctl restart=.
- *=535= even with the right password.* Check the listener exists and is
  =vpopmail:vchkpw= (=ls -l /var/run/dovecot/auth-client-smtp=); a missing or
  wrong-owner socket means the bridge cannot connect and dovecot never sees the
  attempt. Reload dovecot to recreate it.
- *IMAP works but SMTP-AUTH fails for a system user.* The row exists in
  =/etc/dovecot/system-passwd= but the passwd-file passdb is not in submission's
  chain, or =result_failure = continue= is missing so the chain stops at
  vpopmail. Verify dovecot's =passdb= ordering.
- *=454= / transient on AUTH.* The bridge exits 111 — dovecot is down, the socket
  is unreachable, or the 10-second timeout fired. Check =journalctl -u dovecot=.
- *AUTH ok but =MAIL FROM= rejected.* =FORCEAUTHMAILFROM= compares the bare AUTH
  name against the envelope sender; AUTH as the full =user@domain= form so the
  identities match (the passdb strips the domain for lookup either way).
- *Self-verify warned on =add=.* =dsmr-smtpauth add= ran the bridge and dovecot
  rejected the just-written row — almost always a dovecot that has not reloaded
  the new listener/passwd-file yet. =systemctl reload dovecot= and re-run
  =dsmr-smtpauth test=.
